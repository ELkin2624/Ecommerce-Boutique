## 3.3.2. Diagramas de Despliegue y Arquitectura Lógica

En estricta conformidad con el estándar formal **OMG Unified Modeling Language (OMG UML) Versión 2.5.1** (Object Management Group, 2017) y las directrices metodológicas de **ICONIX Process** (Rosenberg & Stephens, 2007), la transición hacia la arquitectura de ejecución física y lógica del proyecto **FashionStore SaaS Multitenant** se formaliza mediante dos especificaciones complementarias:
1. **Diagrama de Despliegue Físico (*Deployment Diagram*):** Modela la distribución en tiempo de ejecución de los componentes ejecutables sobre nodos físicos de hardware (`<<device>>`), entornos de ejecución aislados (`<<execution environment>>`), servidores de bases de datos (`<<database server>>`), elementos de enrutamiento y pasarelas perimetrales, detallando las rutas de comunicación seguras, protocolos y puertos de red (Bass et al., 2021).
2. **Diagrama de Paquetes o Capas (*Package Diagram - Arquitectura Lógica*):** Modela la organización modular del código fuente, estructurando el cliente web bajo los estándares de **Feature-Sliced Design (FSD)** y el backend principal bajo los principios de **Clean Architecture** y módulos desacoplados de NestJS, garantizando alta cohesión y bajo acoplamiento con reglas estrictas de dependencias unidireccionales (Fowler, 2002; Martin, 2017).

> [!NOTE]
> **Normativa de Representación y Colores en OMG UML 2.5.1:**  
> De acuerdo con la especificación oficial de la OMG (sección 7.2.4, *Graphic Paths and Graphical Information*), el estándar UML **no prescribe ni impone paletas de color para los símbolos o nodos**. Las herramientas comerciales como Enterprise Architect aplican por defecto gradientes de color propios de su tema visual (tonos pasteles o amarillentos); sin embargo, en la literatura académica formal y en la documentación técnica rigurosa se utiliza la notación **monocromática / escala de grises estándar** (fondo blanco `#FFFFFF`, trazos negros `#000000`, tipografía nítida e iconos estereotipados normalizados). Los artefactos XMI generados para este proyecto han sido parametrizados explícitamente bajo este estándar académico limpio.

### 3.3.2.1. Diagrama de Despliegue Físico (Topología de Infraestructura)

La topología de despliegue de FashionStore implementa una infraestructura distribuida y resiliente, organizada en los siguientes nodos principales:

1. **`Dispositivo Cliente - PC / Laptop / Smartphone` (`<<device>>`):**
   - Terminales de trabajo del cajero en tienda física (POS) y smartphones de clientes que acceden al e-commerce y vestidor virtual.
   - Aloja el entorno de ejecución `Navegador Web - Runtime Móvil (<<execution environment>>)` (Chromium V8 en escritorio / React Native Hermes Engine en móvil).
   - Ejecuta los componentes de software del cliente:
     - `App Web FashionStore (<<component>>)`: React 19 + Vite, SPA modular, FSD y Recharts.
     - `App Móvil FashionStore (<<component>>)`: React Native 0.86+, AR Vision con MediaPipe y Shopify Skia (aceleración por GPU).
     - `Almacenamiento Local Offline (<<component>>)`: Base de datos IndexedDB gestionada con Dexie.js (cola Outbox transaccional `syncQueue`) y SQLite local en smartphones para garantizar operación sin Internet (CU-15 y CU-16).

2. **`Router Local - Gateway Cliente` (`<<device>>`):**
   - Concentrador de red local (Ethernet cableado para cajas POS, Wi-Fi o red de datos móviles 4G/5G).
   - Se comunica con el dispositivo cliente mediante enlace local y con el exterior a través de la red WAN.

3. **`Router Perimetral & Firewall` (`<<device>>`):**
   - Pasarela de borde y seguridad perimetral (Cloudflare WAF / GCP Cloud Armor y balanceador de carga).
   - Recibe el tráfico cifrado de Internet bajo `TLS 1.3 / SSL` en puertos públicos estándar (`HTTPS :443` y `WSS :443`).
   - Enruta la descarga de activos estáticos hacia el almacenamiento en la nube y reenvía el tráfico transaccional a la subred privada de cómputo.

4. **`Servidor de Almacenamiento Estático` (`<<device>>`):**
   - Infraestructura de almacenamiento de objetos estáticos en **Amazon Web Services (AWS S3 + CloudFront CDN)**.
   - Aloja los componentes:
     - `Bucket Web Assets`: Distribución de la PWA web compilada (HTML5, JS, CSS, iconos).
     - `Bucket Media Texturas WebP y Fotos Catálogo`: Almacenamiento de alta durabilidad para texturas textiles transparentes y modelos para realidad aumentada.

5. **`Servidor de Aplicaciones` (`<<device>>`):**
   - Nodo de cómputo en **Google Cloud Run (Linux Host / Serverless Containers)** en subred privada.
   - Aloja el `Motor Docker Engine (<<execution environment>>)`, el cual ejecuta tres contenedores desacoplados:
     - `Contenedor Backend Core (<<component>>)`: NestJS 12 sobre Node.js 20 en el puerto `:3000` (autenticación JWT, RBAC, catálogo, inventario, reservas, órdenes y lógica SaaS multitenant).
     - `Contenedor Microservicio IA (<<component>>)`: FastAPI sobre Python 3.11 en el puerto `:8000` (motor ReportIQ con *Zero SQL Injection*, deformación de mallas textiles AR y recomendaciones).
     - `Contenedor WebSockets (<<component>>)`: NestJS Gateway en el puerto `:3001` (alertas en tiempo real, conciliación de reservas y sincronización reactiva de cajas POS).

6. **`Servidor de Base de Datos` (`<<database server>>`):**
   - Clúster de base de datos relacional administrado en **Amazon RDS Multi-AZ**.
   - Aloja el `Motor Relacional PostgreSQL 16 & Redis 7 (<<execution environment>>)` conectado al servidor de aplicaciones por red interna TCP/IP segura en puerto `:5432` mediante el pool de conexiones de Prisma ORM:
     - `Base de Datos - fashionstore_db (<<component>>)`: Implementa el aislamiento lógico-físico multitenant mediante el esquema central `public` (usuarios globales, empresas, suscripciones) y los esquemas dedicados e independientes `tenant_<slug>` gobernados por `search_path` (catálogos, stock, kardex, órdenes y pagos).
     - `Almacén Redis 7 (<<component>>)`: Instancia en memoria AWS ElastiCache en puerto `:6379` para limitación de tasa (*Token Bucket*), control de concurrencia y lista negra de tokens revocados.

7. **`Servicios Externos en la Nube` (`<<device>>`):**
   - `Plataforma Stripe (PCI-DSS Cloud)`: Gestión recurrente de suscripciones SaaS (CU-18) y verificación criptográfica HMAC de webhooks.
   - `Google Gemini AI Infrastructure`: Inferencia de lenguaje natural para traducción de consultas directivas en ReportIQ (CU-20).

### 3.3.2.2. Diagrama de Paquetes y Arquitectura Lógica

La arquitectura lógica organiza el código fuente del monorepo distribuido en tres subsistemas claramente desacoplados:

1. **Frontend Web & POS (Feature-Sliced Design - FSD):**
   - `Layer::app`: Inicialización global, enrutador, proveedores (`React Query`, `StripeProvider`) y estilos base.
   - `Layer::pages`: Vistas ensambladoras (`PosPage`, `StoresPage`, `ReportsPage`, `CatalogPage`).
   - `Layer::widgets`: Componentes compuestos de alta complejidad (`Navbar`, `Sidebar`, `PosSyncModal`, `ReceiptModal`).
   - `Layer::features`: Casos de uso de negocio interactivos (`pos`, `cart`, `checkout`, `saas`, `inventory`, `promotions`).
   - `Layer::entities`: Modelos del dominio del cliente (`user`, `product`, `order`, `branch`, `tenant`).
   - `Layer::shared`: Reutilizables libres de lógica de negocio (`apiClient`, `offlineDexie`, `uiPrimitives` con CVA, `libRbac`).
   - *Regla Estricta FSD:* El flujo de importaciones es estrictamente descendente (`pages` $\rightarrow$ `widgets` $\rightarrow$ `features` $\rightarrow$ `entities` $\rightarrow$ `shared`).

2. **Backend Transaccional (NestJS Clean Architecture):**
   - `Presentation Layer`: Controladores REST, DTOs con `class-validator`, guardias JWT/RBAC e interfaz OpenAPI Swagger.
   - `Application Layer`: Servicios de casos de uso (`OrdersService`, `SaasService`, `InventoryService`, `ReportsService`) y tareas Cron desatendidas.
   - `Domain Layer`: Reglas puras del negocio (cálculo de impuestos IVA, políticas de stock en Kardex y límites de cuotas por plan SaaS).
   - `Infrastructure Layer`: Adaptadores a base de datos (`PrismaService`, esquemas `tenant_<slug>`), Redis, Stripe SDK y microservicio de IA.
   - *Inversión de Dependencias (DIP):* La infraestructura implementa y depende de las abstracciones definidas en el dominio y la aplicación.

3. **Microservicio de IA (Python FastAPI Modular):**
   - `app.core`: Configuración de entorno con `pydantic-settings`, seguridad con Argon2id y JWT.
   - `app.database`: Sesiones asíncronas de `SQLAlchemy 2.0`, conexión con `Psycopg 3` y migraciones `Alembic`.
   - `modules`: `generative_reports` (ReportIQ con *Zero SQL Injection*), `virtual_fitting` (Pillow y texturas WebP), `recommendations` y `assistant`.
   - `app.services`: Clientes de integración con `Boto3` (AWS S3) y `HTTPX` (Google Gemini API).

## 3.3.5. Integración de Componentes

La integración de componentes en la plataforma **FashionStore SaaS Multitenant** describe los mecanismos formales mediante los cuales los distintos subsistemas desacoplados (Frontend Web/POS, Aplicación Móvil, API Gateway en NestJS, Microservicio de Inteligencia Artificial en FastAPI, Motor Relacional PostgreSQL 16 y servicios de infraestructura externa) se conectan, dialogan y colaboran de forma segura y coordinada (Fowler, 2018; Rosenberg & Stephens, 2007).

Bajo la especificación oficial de **OMG UML 2.5.1** (Object Management Group, 2017, Capítulo 11 *Structured Classifiers*, Sección 11.6 *Components*), un **Diagrama de Componentes** modela la arquitectura de software en términos de unidades modulares reemplazables e independientes que exponen sus funcionalidades a través de **interfaces provistas (*Provided Interfaces*)** y consumen servicios mediante **interfaces requeridas (*Required Interfaces*)**.

La especificación OMG UML 2.5.1 estipula formalmente diversas opciones notacionales complementarias para representar este diálogo entre componentes (Sección 11.6.4 y 11.6.5):
1. **Notación de Piruleta y Enchufe (*Ball-and-Socket / Lollipop & Socket*, Figura 11.40 y 11.46):** Representación gráfica compacta de caja negra donde las interfaces provistas se muestran como círculos (*lollipops*) y las requeridas como semicírculos (*sockets*) saliendo del límite del componente.
2. **Notación de Clasificadores Explícitos con Dependencias (*Explicit Representation using Dependency notation*, Figura 11.43):** Representación formal y detallada donde cada interfaz se modela como un clasificador rectangular independiente (`«interface»`) con su compartimento de operaciones (`operations`). La provisión de la interfaz se modela mediante una relación de **Realización** (flecha discontinua con triángulo cerrado hueco, `Realization`, apuntando del componente a la interfaz), mientras que el consumo se modela mediante una relación de **Dependencia** (flecha discontinua abierta con estereotipo `«use»`, `Usage / Dependency`, apuntando del componente a la interfaz requerida).
3. **Notación de Visión General con Dependencias Directas (Figura 11.39):** Diagrama de alto nivel que conecta directamente componentes con arcos de dependencia estereotipados (`«use»`).

En el presente proyecto se adopta la **Notación Explícita de la Figura 11.43 de UML 2.5.1** en combinación con Enterprise Architect, puesto que —como prescribe textualmente la norma de la OMG— es la única notación que permite visibilizar el detalle de las operaciones del contrato de integración (métodos, firmas, protocolos y puertos de red), facilitando la trazabilidad hacia la implementación real. Adicionalmente, el modelo permite a los evaluadores conmutar a la vista gráfica de piruletas (*Use Circle Notation*) con un solo clic dentro de Enterprise Architect.

### 3.3.5.1. Diagrama de Componentes del Sistema (UML 2.5.1)

El ecosistema de software se descompone en 8 componentes funcionales e infraestructurales, vinculados mediante interfaces formales tipificadas por protocolo y puerto de red:

1. **Frontend Web & POS Client (`<<component>>`):** Aplicación de página única (SPA) desarrollada en React 18 y Vite, organizada bajo el estándar *Feature-Sliced Design* (FSD). Alberga la tienda virtual omnicanal, el panel administrativo SaaS y el punto de venta (*POS*) en mostrador con motor de persistencia local en Dexie.js (IndexedDB).
2. **App Móvil FashionStore (`<<component>>`):** Aplicación nativa desarrollada en React Native y Expo. Integra la cámara de ultra baja latencia con *Vision Camera* y renderizado gráfico acelerado por hardware con *Shopify Skia* para el probador virtual en Realidad Aumentada (AR).
3. **Backend Core & API Gateway (`<<component>>`):** Servidor transaccional orquestado en NestJS (Node.js 20). Actúa como punto central de entrada, enrutamiento multitenant, emisor de identidad criptográfica JWT, orquestador de base de datos relacional y servidor de eventos WebSocket bidireccionales.
4. **Microservicio de IA & Reportes (`<<component>>`):** Servicio analítico especializado desarrollado en FastAPI (Python 3.11). Implementa el motor determinista **ReportIQ** para analítica empresarial en lenguaje natural, recomendación de tallas corporales y preprocesamiento de texturas textiles.
5. **Motor de Base de Datos (`<<component>>`):** Instancia de PostgreSQL 16 con arquitectura multitenant basada en aislamiento lógico de esquemas (`schema-per-tenant`), control de concurrencia multiversión (MVCC) y transacciones ACID.
6. **Almacenamiento de Objetos & CDN (`<<component>>`):** Bucket de AWS S3 respaldado por la red de distribución de contenidos Amazon CloudFront, encargado de servir imágenes de catálogo y texturas de prendas con compresión WebP.
7. **Pasarela de Pagos Externa (`<<component>>`):** Plataforma Stripe Cloud API (certificada PCI-DSS Nivel 1) para la tokenización de tarjetas bancarias, autorización de compras y verificación de webhooks.
8. **Plataforma LLM Externa (`<<component>>`):** API de Google Gemini 1.5 Flash para el procesamiento semántico de lenguaje natural bajo esquemas estructurados de Pydantic.

### 3.3.5.3. Integración en Tiempo Real y Comunicación Asíncrona

#### 1. Canal WebSocket (WSS) para Alertas en Sucursales y Probadores
Para las funciones que requieren sincronización inmediata en planta física (pantallas de inventario en mostrador, probadores inteligentes y notificación de ventas *offline* recién conciliadas), se implementó un canal dúplex basado en el protocolo **WebSocket seguro (WSS)** mediante el módulo de *WebSockets Gateway* de NestJS (puerto `3001`):

* **Aislamiento Multitenant por Salas (*Rooms*):** Para evitar la fuga de eventos entre marcas comerciales o tiendas distintas, los clientes se suscriben a salas particionadas deterministamente siguiendo la convención:
  $$\text{Canal} = \text{tenant\_}\langle\text{slug}\rangle\text{\_branch\_}\langle\text{branch\_id}\rangle$$
* **Eventos Principales:**
  1. `join_branch`: El cliente web o móvil envía su token JWT y solicita unirse a la sala de su sucursal autorizada.
  2. `new_offline_order_synced`: Disparado por el servidor al momento en que una terminal POS encola y procesa una venta realizada sin conexión a Internet, actualizando el Kardex de existencias en todas las terminales de la tienda de manera instantánea.
  3. `virtual_tryon_session_start`: Notificación emitida desde la aplicación móvil hacia el terminal de mostrador cuando un cliente inicia una prueba virtual AR en la tienda, permitiendo a los dependientes preparar el stock físico.

#### 2. Integración HTTP Interna entre NestJS y FastAPI mediante HTTPX
La comunicación entre el API Gateway en NestJS y el microservicio analítico en FastAPI se efectúa a través de una red privada virtual (*Virtual Private Cloud*) sin exposición directa a la Internet pública:

* **Cliente HTTP Asíncrono no Bloqueante:** NestJS utiliza un adaptador de cliente HTTP configurado con un pool de conexiones persistentes (*Keep-Alive*) y una política estricta de tiempo de espera (*timeout*) de 5.000 ms.
* **Propagación del Contexto de Inquilino:** En cada solicitud interna dirigida al puerto `8000` de FastAPI, NestJS inyecta dos cabeceras privadas de control:
  * `X-Internal-Secret`: Clave criptográfica precompartida de alta entropía que valida que la solicitud proviene legítimamente del API Gateway y no de un actor malicioso en la red local.
  * `X-Tenant-Schema`: Identificador del esquema relacional (`tenant_<slug>`) sobre el cual FastAPI debe contextualizar sus consultas analíticas.
* **Resiliencia ante Fallas (*Circuit Breaker*):** En caso de indisponibilidad temporal o sobrecarga en el microservicio de IA, el cliente HTTP de NestJS conmuta automáticamente a un modo de degradación elegante (*graceful fallback*), retornando agregaciones analíticas calculadas de forma determinista mediante consultas SQL estándar predefinidas.

### 3.3.5.4. Políticas de Seguridad y Aislamiento en la Integración

#### 1. Esquema de Autenticación Unificada mediante JWT Stateless
Para mantener el desacoplamiento entre el núcleo transaccional (NestJS) y el microservicio analítico (FastAPI) sin sobrecargar la base de datos con consultas recurrentes de validación de sesión:

1. **Emisión de Identidad Centralizada:** NestJS genera tokens **JSON Web Tokens (JWT)** firmados criptográficamente mediante el algoritmo simétrico **HMAC-SHA256 (HS256)** al momento del inicio de sesión.
2. **Estructura Estándar de los *Claims* del Token:**
   * `sub`: Identificador único global del usuario (`UUID v4`).
   * `email`: Correo corporativo del operador.
   * `tenantSlug`: Identificador de la tienda activa en el momento de la emisión.
   * `role`: Rol del usuario dentro de la organización (`SUPER_ADMIN`, `OWNER`, `MANAGER`, `CASHIER`, `CLIENT`).
   * `exp`: Tiempo de expiración estricto (15 minutos para tokens de acceso, renovables con *Refresh Token* de 7 días).
3. **Validación Desacoplada en FastAPI:**
   * Ambos microservicios comparten la variable de entorno `JWT_SECRET` inyectada mediante secretos de infraestructura (Google Secret Manager / Docker Secrets).
   * El microservicio FastAPI dispone de una dependencia de seguridad nativa (`JWTBearer`) que decodifica y verifica la firma del token de forma completamente matemática y autónoma en memoria, sin realizar llamadas HTTP ni consultas a PostgreSQL para autenticar la petición.

#### 2. Aislamiento de Base de Datos y Privilegios Mínimos entre Servicios
Siguiendo el principio de menor privilegio (*Principle of Least Privilege*):

* **Rol de Conexión de NestJS (`app_rw_user`):** Posee permisos de lectura, inserción, actualización y eliminación de datos (`SELECT`, `INSERT`, `UPDATE`, `DELETE`) sobre todos los esquemas, además de privilegios de definición de datos (`CREATE SCHEMA`) para el aprovisionamiento automatizado de nuevas marcas.
* **Rol de Conexión de FastAPI (`analytics_ro_user`):** Usuario restringido de base de datos con permisos estrictos de solo lectura (`SELECT`). Este usuario tiene revocado el acceso de modificación (`UPDATE`, `DELETE`, `DROP`, `ALTER`), lo que garantiza matemáticamente que ninguna vulnerabilidad o manipulación de lenguaje natural a través de ReportIQ pueda alterar o borrar registros contables de la plataforma.
* **Inyección Forzada de `search_path`:** Antes de ejecutar cualquier consulta parametrizada generada por el motor analítico, FastAPI ejecuta la instrucción de sesión:
  $$\text{SET search\_path TO tenant\_}\langle\text{slug}\rangle\text{, public;}$$
  lo que garantiza el hermetismo absoluto entre inquilinos.

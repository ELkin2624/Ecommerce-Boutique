## 3.3.3. Implementación de la Base de Datos

En el desarrollo de **FashionStore SaaS Multitenant**, la persistencia física de datos no se construyó mediante la ejecución estática y manual de scripts SQL artesanales (`CREATE TABLE ...`), sino mediante una arquitectura moderna de **Mapeo Objeto-Relacional (ORM)** fuertemente tipado con **Prisma ORM v6**, combinada con **aprovisionamiento dinámico de esquemas en tiempo de ejecución (Schema-per-Tenant)** y **almacenamiento local estructurado (IndexedDB / SQLite)** para soportar la operación desconectada (*Offline-First*).

El diseño físico da cumplimiento riguroso a los requisitos no funcionales de **Aislamiento de Datos (RNF02)**, **Persistencia Offline (RNF03)**, **Integridad Transaccional (RNF04)** e **Idempotencia (RNF05)**. A continuación, se detallan los cuatro componentes físicos implementados en el código fuente del proyecto.

### 3.3.3.1. Aislamiento Multitenant en Código (Aprovisionamiento Dinámico DDL)

Para garantizar que ninguna empresa pueda leer, modificar o contaminar los datos comerciales de otra (**RNF02**), se adoptó el patrón **Esquema Dedicado por Inquilino (*Schema-per-Tenant*)** sobre un clúster PostgreSQL compartido. 

En lugar de requerir migraciones manuales ejecutadas por un administrador de sistemas cada vez que se registra una boutique, el servicio de aprovisionamiento de NestJS (`TenantProvisioningService`) crea y clona físicamente el esquema de base de datos en tiempo de ejecución.

#### Extracto de Implementación: `backend/src/modules/saas/tenant-provisioning.service.ts`

El servicio ejecuta la creación atómica mediante sentencias DDL nativas invocadas a través de `this.prisma.publicClient.$executeRawUnsafe`:

```typescript
// backend/src/modules/saas/tenant-provisioning.service.ts

const TABLES_IN_ORDER = [
  'roles',
  'permissions',
  'role_permissions',
  'users',
  'user_roles',
  'refresh_tokens',
  'categories',
  'seasons',
  'collections',
  'suppliers',
  'products',
  'product_variants',
  'product_images',
  'cities',
  'branches',
  'inventory_locations',
  '_SharedWarehouses',
  'inventory_stocks',
  'inventory_movements',
  'reservations',
  'reservation_items',
  'carts',
  'cart_items',
  'orders',
  'order_items',
  'payments',
  'promotions',
];

@Injectable()
export class TenantProvisioningService {
  private readonly logger = new Logger(TenantProvisioningService.name);

  constructor(private readonly prisma: PrismaService) {}

  async createTenant(dto: CreateTenantDto, options?: CreateTenantOptions) {
    // 1. Sanitización estricta del slug y cálculo del nombre del esquema físico
    const cleanSlug = dto.slug.toLowerCase().trim().replace(/[^a-z0-9-]/g, '');
    const schemaName = `tenant_${cleanSlug.replace(/-/g, '_')}`;

    // Validación de seguridad para prevenir inyecciones SQL en identificadores DDL
    if (!/^tenant_[a-z0-9_]{3,60}$/.test(schemaName)) {
      throw new BadRequestException('El nombre de esquema generado no es seguro o válido.');
    }

    const client = this.prisma.publicClient;

    // 2. Registro transaccional del Inquilino en el esquema public con Advisory Locks
    const reservation = await client.$transaction(async (tx) => {
      await tx.$executeRawUnsafe(
        `SELECT pg_advisory_xact_lock(hashtext($1));`,
        `slug:${cleanSlug}`,
      );

      return tx.tenant.create({
        data: {
          name: dto.name.trim(),
          slug: cleanSlug,
          schemaName: schemaName,
          plan: dto.plan || 'STARTER',
          status: 'PROVISIONING',
          ownerName: dto.ownerName,
          ownerEmail: dto.ownerEmail.toLowerCase().trim(),
        },
      });
    });

    // 3. Creación física del esquema PostgreSQL dedicado
    await client.$executeRawUnsafe(`CREATE SCHEMA IF NOT EXISTS "${schemaName}";`);

    // 4. Replicación de tipos ENUM de PostgreSQL en el nuevo esquema
    const enumDefinitions = [
      { name: 'LocationType', values: ['WAREHOUSE', 'SALES_FLOOR'] },
      { name: 'MovementType', values: ['PURCHASE_RECEIPT', 'TRANSFER', 'RESERVATION_HOLD', 'RESERVATION_RELEASE', 'SALE', 'RETURN', 'ADJUSTMENT'] },
      { name: 'ReservationStatus', values: ['PENDING', 'CONFIRMED', 'PREPARED', 'READY', 'COMPLETED', 'CANCELLED', 'EXPIRED'] },
      { name: 'OrderType', values: ['ONLINE', 'IN_STORE'] },
      { name: 'OrderStatus', values: ['PENDING', 'PAID', 'DELIVERED', 'CANCELLED'] },
      { name: 'PaymentMethod', values: ['CASH', 'CARD', 'QR', 'GATEWAY'] },
      { name: 'PaymentStatus', values: ['PENDING', 'SUCCESS', 'FAILED'] },
    ];

    for (const enumDef of enumDefinitions) {
      const valuesLiteral = enumDef.values.map((v) => `'${v}'`).join(', ');
      await client.$executeRawUnsafe(`
        DO $$ BEGIN
          CREATE TYPE "${schemaName}"."${enumDef.name}" AS ENUM (${valuesLiteral});
        EXCEPTION
          WHEN duplicate_object THEN null;
        END $$;
      `);
    }

    // 5. Clonación física de tablas maestras con LIKE public."tabla" INCLUDING ALL
    // La cláusula INCLUDING ALL clona columnas, tipos, defaults, restricciones e índices
    for (const table of TABLES_IN_ORDER) {
      await client.$executeRawUnsafe(
        `CREATE TABLE IF NOT EXISTS "${schemaName}"."${table}" (LIKE public."${table}" INCLUDING ALL);`,
      );
    }

    // 6. Conversión explícita de columnas a los tipos ENUM locales del inquilino
    for (const ec of enumColumns) {
      await client.$executeRawUnsafe(
        `ALTER TABLE "${schemaName}"."${ec.table}" ALTER COLUMN "${ec.column}" DROP DEFAULT;`,
      );
      await client.$executeRawUnsafe(
        `ALTER TABLE "${schemaName}"."${ec.table}" ALTER COLUMN "${ec.column}" TYPE "${schemaName}"."${ec.enumName}" USING ("${ec.column}"::text::"${schemaName}"."${ec.enumName}");`,
      );
      if (ec.defaultValue) {
        await client.$executeRawUnsafe(
          `ALTER TABLE "${schemaName}"."${ec.table}" ALTER COLUMN "${ec.column}" SET DEFAULT '${ec.defaultValue}'::"${schemaName}"."${ec.enumName}";`,
        );
      }
    }

    // 7. Recreación de Claves Foráneas (Foreign Keys) internas del esquema
    // Mediante introspección dinámica de pg_catalog.pg_constraint
    const fks = await client.$queryRawUnsafe(`
      SELECT
        rel.relname AS table_name,
        att.attname AS column_name,
        frel.relname AS foreign_table_name,
        fatt.attname AS foreign_column_name,
        con.conname AS constraint_name
      FROM pg_catalog.pg_constraint con
      JOIN pg_catalog.pg_namespace nsp ON nsp.oid = con.connamespace
      JOIN pg_catalog.pg_class rel ON rel.oid = con.conrelid
      JOIN pg_catalog.pg_class frel ON frel.oid = con.confrelid
      JOIN pg_catalog.pg_attribute att ON att.attrelid = con.conrelid AND att.attnum = con.conkey[1]
      JOIN pg_catalog.pg_attribute fatt ON fatt.attrelid = con.confrelid AND fatt.attnum = con.confkey[1]
      WHERE con.contype = 'f' AND nsp.nspname = 'public' AND array_length(con.conkey, 1) = 1;
    `);

    for (const fk of fks as any[]) {
      try {
        const cName = `${fk.table_name}_${fk.column_name}_fkey`.substring(0, 60);
        await client.$executeRawUnsafe(`
          ALTER TABLE "${schemaName}"."${fk.table_name}"
          ADD CONSTRAINT "${cName}"
          FOREIGN KEY ("${fk.column_name}")
          REFERENCES "${schemaName}"."${fk.foreign_table_name}" ("${fk.foreign_column_name}")
          ON DELETE CASCADE ON UPDATE CASCADE;
        `);
      } catch {
        // Restricción existente ignorada
      }
    }

    // 8. Sembrado inicial de seguridad RBAC base
    await client.$executeRawUnsafe(
      `INSERT INTO "${schemaName}".roles SELECT * FROM public.roles ON CONFLICT DO NOTHING;`,
    );

    // 9. Activación definitiva del inquilino
    await client.tenant.update({
      where: { id: reservation.id },
      data: { status: 'ACTIVE' },
    });
  }
}
```

### 3.3.3.3. Estrategia de Conexión Dinámica y Conmutación de `search_path`

En una arquitectura multitenant basada en esquemas dedicados, la aplicación debe dirigir cada consulta de base de datos al esquema correspondiente de forma transparente para los servicios de negocio. En FashionStore, esto se resolvió combinando tres capas técnicas:

1. **`TenantMiddleware` (Extracción e Inyección de Contexto):**  
   Intercepta toda petición HTTP entrante, identifica al inquilino mediante la cabecera `X-Tenant-Slug`, `X-Tenant-ID` o el subdominio del host (`slug.fashionstore.app`), y valida su estado `ACTIVE` en `public.tenants`. Luego, encapsula la ejecución en un almacén asíncrono con `AsyncLocalStorage`.

2. **`TenantContext` (Contexto Asíncrono no Bloqueante):**  
   Basado en la API nativa de Node.js `node:async_hooks`, almacena el `schemaName` activo de forma aislada para cada solicitud concurrente sin riesgo de condiciones de carrera entre hilos.

3. **`PrismaService` con Proxy Transparente y `TenantConnectionManager`:**  
   `PrismaService` envuelve la instancia de Prisma en un objeto **JavaScript Proxy**. Cuando un servicio invoca cualquier modelo de catálogo o ventas (ej. `this.prisma.order.findMany()`), el Proxy consulta `TenantContext.getSchema()`. Si existe un esquema activo distinto de `public`, delega la llamada a un `PrismaClient` específico para ese esquema, administrado por un pool interno en memoria (`Map<string, PrismaClient>`).

#### A. Middleware de Enrutamiento de Inquilino

```typescript
// backend/src/common/multitenancy/tenant.middleware.ts

@Injectable()
export class TenantMiddleware implements NestMiddleware {
  constructor(private readonly prisma: PrismaService) {}

  async use(req: Request, res: Response, next: NextFunction) {
    // 1. Detección del inquilino (Headers HTTP, Query param o Subdominio)
    const tenantIdentifier =
      (req.headers['x-tenant-slug'] as string) ||
      (req.headers['x-tenant-id'] as string) ||
      (req.query.tenant_slug as string);

    // 2. Consulta y validación contra el plano central public.tenants
    const tenant = await this.prisma.publicClient.tenant.findFirst({
      where: { slug: tenantIdentifier.toLowerCase().trim() },
    });

    if (!tenant || tenant.status !== 'ACTIVE') {
      throw new ForbiddenException(`Inquilino no válido o suspendido.`);
    }

    // 3. Establece el contexto asíncrono para la duración exacta de la petición
    return TenantContext.run(
      {
        tenantId: tenant.id,
        tenantSlug: tenant.slug,
        schemaName: tenant.schemaName,
      },
      () => {
        res.setHeader('X-Tenant-Schema', tenant.schemaName);
        next();
      },
    );
  }
}
```

#### B. Gestor Dinámico de Conexiones (`search_path` de PostgreSQL)

Al instanciar un cliente para un inquilino específico, `TenantConnectionManager` parametriza la URL de conexión añadiendo el parámetro de consulta `?schema=tenant_<slug>`. En el protocolo de comunicación de PostgreSQL, este parámetro configura de forma predeterminada la variable de sesión `search_path`:

$$\text{search\_path} = \text{"tenant\_<slug>"}, \text{public}$$

```typescript
// backend/src/prisma/tenant-connection-manager.ts

@Injectable()
export class TenantConnectionManager implements OnModuleDestroy {
  private readonly clients = new Map<string, PrismaClient>();
  private readonly baseDbUrl: string = process.env.DATABASE_URL!;

  getClientForSchema(schemaName: string): PrismaClient {
    // Retorna la conexión existente del pool en memoria si ya fue instanciada
    if (this.clients.has(schemaName)) {
      return this.clients.get(schemaName)!;
    }

    // Construye la URL asignando el search_path hacia el esquema del inquilino
    const parsed = new URL(this.baseDbUrl);
    parsed.searchParams.set('schema', schemaName);
    const tenantDbUrl = parsed.toString();

    const client = new PrismaClient({
      datasources: { db: { url: tenantDbUrl } },
    });

    this.clients.set(schemaName, client);
    return client;
  }

  async onModuleDestroy() {
    // Cierre ordenado de todas las conexiones activas en el pool al apagar el servidor
    for (const [schema, client] of this.clients.entries()) {
      await client.$disconnect();
    }
    this.clients.clear();
  }
}
```

#### C. Proxy Transparente en PrismaService

```typescript
// backend/src/prisma/prisma.service.ts

@Injectable()
export class PrismaService extends PrismaClient implements OnModuleInit, OnModuleDestroy {
  constructor(private readonly connectionManager: TenantConnectionManager) {
    super();

    return new Proxy(this, {
      get(target: PrismaService, prop: string | symbol, receiver: any) {
        // Modelos SaaS centrales siempre van al esquema 'public'
        if (prop === 'tenant' || prop === 'tenantMembership' || prop === 'publicClient') {
          const val = Reflect.get(target, prop, target);
          return typeof val === 'function' ? (val as any).bind(target) : val;
        }

        // Obtener el esquema activo en la solicitud actual
        const schema = TenantContext.getSchema();
        if (schema && schema !== 'public') {
          const tenantClient = target.connectionManager.getClientForSchema(schema);
          const val = Reflect.get(tenantClient, prop, tenantClient);
          return typeof val === 'function' ? val.bind(tenantClient) : val;
        }

        // Esquema por defecto
        const val = Reflect.get(target, prop, receiver);
        return typeof val === 'function' ? val.bind(target) : val;
      },
    });
  }
}
```

### 3.3.3.4. Almacenamiento Local Offline (IndexedDB con Dexie.js y SQLite Móvil)

Para posibilitar el cobro en mostrador sin conexión a Internet (**CU-15 y CU-16**) y salvaguardar los registros ante cortes de energía o cierres intempestivos del navegador o aplicación (**RNF03**), se implementaron motores de persistencia local relacional y transaccional tanto en el cliente Web PWA como en el cliente Móvil.

#### A. Persistencia Web PWA: IndexedDB con Dexie.js (`app-db.ts`)

En el cliente web Angular / React PWA, la librería **Dexie.js v4** abstrae el motor nativo IndexedDB del navegador proporcionando almacenamiento transaccional indexado y tipado.

La estructura clave es la tabla **`syncQueue`** (implementación del patrón de arquitectura *Transactional Outbox Pattern* en el cliente), encargada de retener las ventas, reservas y modificaciones locales pendientes de envío al servidor.

```typescript
// frontend/src/shared/offline/db/app-db.ts

import Dexie, { type Table } from 'dexie';
import type {
  OfflineProduct,
  OfflineCategory,
  OfflineBranch,
  OfflineCustomer,
  OfflineOrder,
  OfflineInventory,
  OutboxItem,
  KVCacheItem,
} from '../types';

export class AppOfflineDatabase extends Dexie {
  products!: Table<OfflineProduct, string>;
  categories!: Table<OfflineCategory, string>;
  branches!: Table<OfflineBranch, string>;
  customers!: Table<OfflineCustomer, string>;
  orders!: Table<OfflineOrder, string>;
  inventory!: Table<OfflineInventory, string>;
  syncQueue!: Table<OutboxItem, number>;
  kvCache!: Table<KVCacheItem, string>;

  constructor() {
    super('BoutiqueFashionOfflineDB');

    // Esquema versión 1 con índices primarios y secundarios para consultas de alta velocidad
    this.version(1).stores({
      products: 'id, name, categoryId, isActive, isLocalOnly, updatedAt',
      categories: 'id, name, slug',
      branches: 'id, cityId, name, isActive',
      customers: 'id, email, phone, isLocalOnly',
      orders: 'id, orderNumber, customerId, branchId, status, paymentMethod, isLocalOnly, createdAt',
      inventory: 'id, variantId, locationId, quantity',
      syncQueue: '++id, idempotencyKey, entity, action, entityId, status, createdAt',
      kvCache: 'key, expiresAt, updatedAt',
    });
  }

  /**
   * Limpia registros de caché KV expirados para optimizar la cuota de disco
   */
  async purgeExpiredCache(): Promise<number> {
    const now = Date.now();
    const expiredKeys = await this.kvCache
      .where('expiresAt')
      .below(now)
      .primaryKeys();

    if (expiredKeys.length > 0) {
      await this.kvCache.bulkDelete(expiredKeys);
    }
    return expiredKeys.length;
  }

  /**
   * Consulta el uso y límite de almacenamiento físico disponible en el navegador
   */
  async getStorageQuotaInfo(): Promise<{ usedBytes: number; quotaBytes: number; percentage: number } | null> {
    if (typeof navigator !== 'undefined' && 'storage' in navigator && 'estimate' in navigator.storage) {
      const estimate = await navigator.storage.estimate();
      return {
        usedBytes: estimate.usage || 0,
        quotaBytes: estimate.quota || 0,
        percentage: estimate.quota ? ((estimate.usage || 0) / estimate.quota) * 100 : 0,
      };
    }
    return null;
  }

  /**
   * Reseteo transaccional de toda la base de datos (seguridad en cierre de sesión)
   */
  async resetAllData(): Promise<void> {
    await this.transaction('rw', this.tables, async () => {
      for (const table of this.tables) {
        await table.clear();
      }
    });
  }
}

export const offlineDb = new AppOfflineDatabase();
```

```typescript
export type OutboxAction = 'CREATE' | 'UPDATE' | 'DELETE' | 'PATCH';

  status: OutboxStatus;         // Estado de la sincronización
  retryCount: number;           // Contador de reintentos exponenciales
  maxRetries: number;
  lastError?: string;           // Registro de causas de rechazo o conflicto de inventario

  updatedAt: number;
```

#### B. Persistencia Móvil: Esquema SQLite para la Cola Outbox

En el entorno móvil (dispositivos de vendedores y supervisores de tienda), la persistencia local se gestiona a través de un motor relacional embebido **SQLite**, garantizando cumplimiento ACID local idéntico al del navegador. 

El esquema DDL implementado en SQLite para la captura de ventas offline y la cola de salida comprende:

```sql
-- Definición DDL del Almacenamiento Local SQLite en el Dispositivo Móvil

-- 1. Tabla local de cabecera de pedidos/ventas capturadas offline
CREATE TABLE IF NOT EXISTS local_orders (
    id TEXT PRIMARY KEY,                       -- UUID v4 generado en el móvil
    user_id TEXT NOT NULL,
    branch_id TEXT NOT NULL,
    order_type TEXT NOT NULL DEFAULT 'IN_STORE',
    status TEXT NOT NULL DEFAULT 'PAID',       -- Venta de contado cobrada en mostrador
    total NUMERIC(10, 2) NOT NULL,
    idempotency_key TEXT UNIQUE NOT NULL,      -- Clave para deduplicación al sincronizar
    sync_status TEXT NOT NULL DEFAULT 'PENDING',-- PENDING | SYNCING | SYNCED | CONFLICT
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 2. Tabla local de líneas de detalle de pedido
CREATE TABLE IF NOT EXISTS local_order_items (
    id TEXT PRIMARY KEY,
    order_id TEXT NOT NULL,
    variant_id TEXT NOT NULL,
    quantity INTEGER NOT NULL,
    unit_price NUMERIC(10, 2) NOT NULL,
    FOREIGN KEY (order_id) REFERENCES local_orders(id) ON DELETE CASCADE
);

-- 3. Cola Transaccional Outbox (Mobile Outbox Queue)
CREATE TABLE IF NOT EXISTS mobile_outbox_queue (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    idempotency_key TEXT UNIQUE NOT NULL,
    entity_type TEXT NOT NULL,                 -- 'ORDER' | 'RESERVATION' | 'STOCK_ADJUSTMENT'
    operation TEXT NOT NULL,                   -- 'CREATE' | 'UPDATE'
    endpoint TEXT NOT NULL,
    payload TEXT NOT NULL,                     -- Serialización JSON de la transacción completa
    status TEXT NOT NULL DEFAULT 'PENDING',    -- PENDING, SYNCING, FAILED, COMPLETED
    retry_count INTEGER DEFAULT 0,
    error_message TEXT,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    synced_at TIMESTAMP
);

-- Índices de consulta rápida para el motor de sincronización móvil
CREATE INDEX IF NOT EXISTS idx_outbox_status ON mobile_outbox_queue(status);
CREATE INDEX IF NOT EXISTS idx_local_orders_sync ON local_orders(sync_status);
```
